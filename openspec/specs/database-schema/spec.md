# database-schema Specification

## Purpose
Defines the relational schema, table structures, data types, foreign keys, check constraints, partial unique indexes, and append-only database triggers for the 13 domain tables of the Taller Mecánico API.

## Requirements

### Requirement: Mandatory 13 Domain Tables and Column Types
The system SHALL define the 13 mandatory tables (`usuario`, `asignacion_rol`, `intento_acceso`, `evento_seguridad`, `cliente`, `vehiculo`, `repuesto`, `estado_orden`, `orden_trabajo`, `item_orden`, `historial_estado_orden`, `movimiento_stock`, `historial_precio_repuesto`) with exact column names, `TIMESTAMPTZ` for all datetime fields, and `NUMERIC` (`Decimal`) for all monetary amounts.

#### Scenario: Schema inspection verifies table names and data types
- **WHEN** the database metadata or PostgreSQL schema is inspected after migration
- **THEN** all 13 tables exist with exact mandatory column names, every timestamp column uses `TIMESTAMP WITH TIME ZONE`, and monetary columns (`repuesto.precio`, `item_orden.precio_unitario`, `historial_precio_repuesto.precio_anterior`, `historial_precio_repuesto.precio_nuevo`, `orden_trabajo.total`) use `NUMERIC`

### Requirement: Indexed Foreign Keys and Bidirectional Navigation
The system SHALL create an explicit database index on every foreign key column and declare bidirectional ORM relationships (`back_populates`), ensuring `Usuario.cliente` resolves to a single optional object (`Cliente | None`) rather than a list.

#### Scenario: Foreign key indexing and 1-to-1 user-client navigation
- **WHEN** the schema indexes and ORM relationships are inspected
- **THEN** every foreign key column has a corresponding index and `Usuario.cliente` is configured with `uselist=False` returning a single `Cliente` instance or `None`

### Requirement: Partial Unique Indexes for Active Records
The system SHALL enforce partial unique indexes on `asignacion_rol(usuario_id, rol) WHERE revocada_en IS NULL`, `vehiculo(patente) WHERE borrado_en IS NULL`, and `repuesto(codigo) WHERE borrado_en IS NULL`.

#### Scenario: Re-registering a soft-deleted license plate or part code succeeds
- **WHEN** a `vehiculo` or `repuesto` has `borrado_en` set to a non-null timestamp and a new row is inserted with the same `patente` or `codigo` and `borrado_en IS NULL`
- **THEN** the database accepts the insertion without a uniqueness conflict

#### Scenario: Duplicate active role assignment or active license plate is rejected
- **WHEN** a second row with the same `(usuario_id, rol)` where `revocada_en IS NULL` or the same `patente` where `borrado_en IS NULL` is inserted
- **THEN** the database raises a unique constraint violation

### Requirement: Domain Check Constraints and Catalog Reference
The system SHALL enforce database `CHECK` constraints on role values, vehicle year (`1950..2100`), part price (`> 0`), part stock (`>= 0`), order total (`>= 0`), item quantity (`> 0`), item unit price (`> 0`), stock movement quantity (`<> 0`), and price history (`precio_nuevo > 0` and `precio_nuevo <> precio_anterior`), and reference `estado_orden.codigo` as a foreign key for order states.

#### Scenario: Invalid domain values or unknown order states are rejected by the database
- **WHEN** an insert or update violates any `CHECK` boundary (e.g., `anio = 1940`, `stock = -1`, `cantidad = 0`, `precio_nuevo = precio_anterior`) or references an `estado` not present in `estado_orden`
- **THEN** PostgreSQL aborts the statement with a constraint violation error

### Requirement: Two-Step Alembic Migrations and Append-Only Triggers
The system SHALL manage schema creation exclusively through two Alembic migrations (never `create_all`): `001` autogenerated for tables, constraints, and indexes, and `002` handwritten to install PL/pgSQL triggers that reject `UPDATE` and `DELETE` on `historial_estado_orden`, `movimiento_stock`, and `historial_precio_repuesto`.

#### Scenario: Full migration cycle upgrade and downgrade succeeds
- **WHEN** `alembic upgrade head`, `alembic downgrade base`, and `alembic upgrade head` are executed sequentially on an empty database
- **THEN** all migrations complete without error, leaving the 13 tables and 3 append-only triggers active

#### Scenario: Append-only triggers block UPDATE and DELETE on historical tables
- **WHEN** an `UPDATE` or `DELETE` statement is executed against `historial_estado_orden`, `movimiento_stock`, or `historial_precio_repuesto`
- **THEN** the database trigger aborts the operation and raises an exception
